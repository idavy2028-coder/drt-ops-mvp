# 通渭县试点下阶段开发与验收总计划

**版本：** 1.0
**编制日期：** 2026-07-26
**适用范围：** 通渭县区域动态响应公交本机业务试点启动前的开发收口、数据准备、联调验收和运行保障。
**执行原则：** 本文档是下阶段唯一执行基线。每个任务完成后必须记录结果、问题和证据，并经过人工审阅后再进入下一项。

## 1. 试点目标与边界

### 1.1 目标

在本机隔离 PostGIS 环境中，验证企业内部运营闭环：调度员通过电话或微信接收需求并录入订单，系统完成站点匹配与调度建议，调度员通过电话或微信向驾驶员下达任务，并在后台代为记录车辆位置和任务节点，最终形成订单、任务、位置事件、审计日志和运营指标闭环。

### 1.2 试点配置

| 项目 | 已确认配置 |
| --- | --- |
| 区域 | 甘肃省通渭县，服务范围以已发布电子围栏为准 |
| 周期 | 1 个月 |
| 运营时段 | 每日 06:30 至 19:00 |
| 车辆与驾驶员 | 4 辆车、4 名驾驶员 |
| 调度员 | 2 名 |
| 需求来源 | 电话、微信，由调度员手工录入 |
| 驾驶员协同 | 电话、微信反馈节点，调度员后台代录 |
| 地图底图 | Leaflet + 合规开放瓦片，不依赖高德 Key |
| 坐标体系 | 业务接口统一 GCJ-02 |
| 数据库 | 自建 PostgreSQL + PostGIS；当前为隔离本机试用库 |

### 1.3 明确不在本阶段实施

- 乘客端、小程序、司机端 App。
- 车载 GPS、连续轨迹追踪和自动司机状态上报。
- 高德 JavaScript Key、白名单、配额接入；后续可作为可选增强。
- OIDC/LDAP、支付结算、行业监管端、多租户和生产级消息队列。
- 复杂全局重排、机器学习预测和生产级实时优化。

## 2. 当前基线

### 2.1 已完成前置能力

- 调度规则组已创建，服务区电子围栏已发布启用。
- 已导入 21 个虚拟站点；地图已支持站点与服务区边界叠加核对。
- 已录入 4 辆车辆、4 名驾驶员。
- 管理端已覆盖订单录入、虚拟站点匹配、调度、人工复核、车辆任务执行、位置历史、审计日志和运营看板。
- 车辆位置管理模块已支持不可变事件、最新快照、服务区外告警、位置审计和历史查询。
- 4 辆现有车辆已补入 `MANUAL_REPORT` 初始位置事件及最新位置快照；新建车辆已改为在同一事务生成车辆、首配位置事件、快照和审计。
- Leaflet 开放瓦片地图已取代高德 Key 依赖。

### 2.2 当前未关闭风险

| 编号 | 风险 | 当前影响 | 处理任务 |
| --- | --- | --- | --- |
| R1 | 4 辆车辆的首配位置被判定在服务区外 | 距离、候选车辆和调度结果可信度不足 | P1-1 |
| R2 | 修复前生成的人工复核订单候选车辆数为 0 | 旧决策不会自动重算 | P1-3 |
| R3 | API 重启后算法容器需要重新绑定网络 | 调度接口可能出现算法连接失败 | P1-4 |

| R5 | 尚未完成 1 万条位置事件、备份恢复和监控告警演练 | 不具备试点启动判定证据 | P4-1 至 P4-3 |
| R6 | 开放瓦片只提供底图，不天然提供地址解析、驾车路径和 ETA | 不可将地图展示能力误认为真实路径服务能力 | P4-5 |

## 4. 执行任务

### P0：代码与环境基线收口

**目标：** 让本机运行环境、代码工作区和验收证据可重复。

| 子任务 | 责任角色 | 前置条件 | 完成标准 |
| --- | --- | --- | --- |
| P0-1 盘点并拆分当前工作区改动 | 开发负责人 | 无 | 已验证改动按“地图与资源配置”“用户与认证”“订单录入”“车辆首配位置”分组；不混入无关文件 |
| P0-2 全量回归与构建 | 开发负责人 | P0-1 | 后端 Maven 测试、前端类型检查、Vitest 和生产构建均通过；失败项有单独记录 |
| P0-3 提交与 PR 收口 | 开发负责人、审阅人 | P0-2 | 每个逻辑分组有可审阅提交；PR 描述包含验证证据和残余风险 |
| P0-4 固化本机启动顺序 | 开发负责人 | P0-2 | 提供单一脚本或 Compose 编排，确保 PostgreSQL、API、算法、前端启动和重启后自动恢复连通 |

### P1：恢复候选车辆调度并验证主链路

**目标：** 关闭“候选车辆 0 个”问题，证明有最新位置快照的空闲车辆可以参与新的调度计算。

| 子任务 | 责任角色 | 前置条件 | 完成标准 |
| --- | --- | --- | --- |
| P1-1 校准 4 辆车首配位置 | 调度主管、调度员 | 已确认车辆实际待命点 | 每辆车通过位置上报写入围栏内的 GCJ-02 坐标；事件为 `MANUAL_REPORT`；最新快照已更新且不再出现服务区外告警 |
| P1-2 核对车辆可调度状态 | 调度员 | P1-1 | 4 辆车均为 `IDLE`、`dispatchable=true`，且存在最新位置快照 |
| P1-3 处理历史人工复核订单 | 调度员 | P1-2 | 修复前候选车辆为 0 的旧决策不得继续确认；已拒绝或取消，并保留审计原因 |
| P1-4 验证算法服务运行依赖 | 开发负责人 | P0-4 或当前容器环境 | API 容器内可访问算法 `/health`；算法不可用时页面显示“算法服务不可用”，不得错误提示为登录失效 |
| P1-5 新建订单调度验收 | 调度员、开发负责人 | P1-1 至 P1-4 | 使用新订单完成录入和调度；候选车辆数大于 0；系统产生自动派单或可确认的人工复核方案 |

### P2：运营基础数据校准

**目标：** 让服务区、站点、车辆、驾驶员、调度规则和账号与通渭县试点配置一致。

| 子任务 | 责任角色 | 前置条件 | 完成标准 |
| --- | --- | --- | --- |
| P2-1 服务区边界复核 | 调度主管、系统管理员 | P1-1 | 在资源配置地图上叠加站点和车辆位置，核对边界覆盖运营范围；必要时以新草稿版本编辑、发布，不直接覆盖历史版本 |
| P2-2 补齐并核验虚拟站点 | 调度主管、调度员 | P2-1 | 站点总数达到 30 至 50 个；每个站点具备名称、地址、GCJ-02 坐标、服务半径和启停状态；导入结果与服务区关系已核验 |
| P2-3 站点启用清单确认 | 调度主管 | P2-2 | 形成“启用、暂不启用、待复核”站点清单；订单匹配仅使用已启用站点 |
| P2-4 车辆与驾驶员台账复核 | 调度主管 | P1-2 | 4 辆车和 4 名驾驶员的车牌、联系电话、可用状态、班次安排和电话/微信联系信息已人工核对 |
| P2-5 第二调度员账号验收 | 系统管理员 | 无 | 创建或确认第 2 名调度员账号；可登录并仅访问订单、调度、任务和位置相关权限，不可管理用户或规则 |
| P2-6 规则参数复核 | 调度主管、系统管理员 | 无 | 确认最大等候 5 分钟、最大绕行 8 分钟、预约窗口 60 分钟、自动阈值 82、人工阈值 62、权重 0.35/0.20/0.30/0.15 和实时插单策略 |

### P3：人工运营闭环验收

**目标：** 用试点实际协作方式跑通从电话需求到任务完成的完整链路。

| 子任务 | 责任角色 | 前置条件 | 完成标准 |
| --- | --- | --- | --- |
| P3-1 即时需求录入验收 | 调度员 | P2 完成 | 调度员可录入乘客姓名、联系方式、人数、起终点、预计出发时间；起终点匹配已启用虚拟站点或人工坐标，并通过围栏校验 |
| P3-2 调度与人工复核验收 | 调度员 | P1-5 | 对自动派单和人工复核各至少完成 1 笔；人工复核可确认或拒绝，理由和决策均进入审计 |
| P3-3 电话/微信下达与反馈台账 | 调度员、驾驶员 | P3-2 | 每笔任务记录下达时间、驾驶员实际反馈时间和调度员录入时间；不将人工录入耗时混入系统等候时长 |
| P3-4 任务节点与位置事件验收 | 调度员 | P3-3 | 按发车、到达上车点、乘客上车、到达目的地、乘客下车、任务完成顺序操作；每个动作产生任务状态、位置事件和审计记录 |
| P3-5 异常流程验收 | 调度员、调度主管 | P3-4 | 分别验证取消、乘客未到、车辆故障和严重延误；确认关联订单、任务和审计记录符合状态机规则 |
| P3-6 结果核对 | 调度主管 | P3-1 至 P3-5 | 订单、任务、位置历史、工作台、审计日志与运营看板对同一业务样本的状态一致 |

### P4：指标、数据安全与运行保障验收

**目标：** 为 1 个月试点建立可解释、可恢复、可监控的运行证据。

| 子任务 | 责任角色 | 前置条件 | 完成标准 |
| --- | --- | --- | --- |
| P4-1 指标口径与样本核对 | 调度主管、开发负责人 | P3-6 | 系统等候时长从“系统录入完成”到“实际上车”；人工录入耗时独立记录；准点率和 ETA 在人工位置阶段仅作参考，不作为硬性上线判定 |
| P4-2 位置事件容量验证 | 开发负责人 | P3-6 | 在隔离库验证约 1 万条位置事件可保留、按车辆/日期查询、导出和快照读取；记录耗时和异常 |
| P4-3 备份恢复与监控演练 | 开发负责人、运维负责人 | P4-2 | 完成每日 PostgreSQL/PostGIS 备份、一次恢复和数据核对；验证 API、算法、数据库健康检查，及超过 30 分钟无位置更新、服务区外位置的告警 |
| P4-4 开放瓦片降级演练 | 调度员、开发负责人 | P3-6 | 瓦片不可用时，调度员仍可通过虚拟站点或经纬度录入位置和订单；系统明确提示地图降级，不阻断业务提交 |
| P4-5 地址、路径与 ETA 能力决策及验收 | 调度主管、开发负责人 | P3-6 | 明确本轮试点采用“虚拟站点/人工坐标 + 当前估算”还是接入合规路径服务；若接入，完成地址解析、驾车距离和 ETA 验收；若暂不接入，书面确认其不作为本机人工试运行硬指标，并将真实路径服务列入下一阶段开发计划 |

### P5：分阶段试运行与启动判定

**目标：** 按已确认订单量逐步扩大，形成“可启动、限条件启动或暂缓启动”的书面结论。

| 周期 | 日订单目标 | 重点验证 |
| --- | --- | --- |
| 第 1 周 | 5 至 10 单/日 | 账号、录单、电话协同、位置补报和基础状态机 |
| 第 2 周 | 20 至 30 单/日 | 调度稳定性、人工复核比例和异常处置 |
| 第 3 周 | 40 至 50 单/日 | 高峰负载、车辆利用和人工录入效率 |
| 第 4 周 | 20 至 50 单/日 | 波动订单量、恢复能力和指标持续性 |

**启动判定条件：**

- 准点率目标不低于 95%，但人工位置阶段仅作为参考指标并标注数据来源。
- 系统等候时长目标不超过 5 分钟，按 P4-1 口径计算。
- 任务完成率不低于 98%。
- 人工复核率不高于 10%。
- 系统可用性不低于 99.5%。
- P0 至 P4 的阻断项全部关闭；未关闭事项必须明确评估为不影响人工试运行，并由调度主管书面接受。

## 6. 执行顺序与禁止事项

### 6.1 强制顺序

`P0 -> P1 -> P2 -> P3 -> P4 -> P5`。

未完成 P1 不得将“候选车辆为 0”的旧人工复核决策作为调度验证结果；未完成 P4 不得宣称具备正式生产上线条件。

### 6.2 禁止事项

- 不直接通过 SQL 修改订单、任务、位置事件、车辆快照、审计日志或规则组。
- 不编辑或删除既有位置事件；位置错误只能以补报或修正事件处理。
- 不将演示坐标、演示账户、隔离库密码写入生产配置或提交到仓库。
- 不以地图瓦片显示成功替代服务区、站点和车辆实际坐标核验。
- 不以人工录入时间替代驾驶员实际反馈时间。
