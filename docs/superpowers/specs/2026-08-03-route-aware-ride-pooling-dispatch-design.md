# 路线感知合乘与车辆启用成本优化设计

## 1. 背景与问题

2026 年 8 月 3 日试运行中，三笔时间相近且线路可衔接的订单依次触发调度：

- 小袁：陇阳镇 → 高铁站，1 人；
- 高士：安川 → 姜滩小学，2 人；
- 刘小光：陇阳镇 → 中医院，1 人。

三笔订单最终分别使用甘 J18817D、甘 J15896D 和甘 J00856D。车辆均为 8 座，三单合计 4 人；从站点关系和承诺时间看，存在由一辆车依次完成的合乘路线。当前三辆车已经发车，本设计不追溯改派，只调整后续新订单的调度行为。

只读排查确认，问题不是车辆、驾驶员或站点数据异常，而是现有调度模型存在以下局限：

1. 每次只评估当前一笔订单，不执行多订单批量全局优化。
2. 新建车辆任务固定标记为同向；既有任务只有在新订单的上下车站都已出现在原任务中且顺序正确时才标记为同向。
3. 新任务和插单任务的预计绕行时间都近似固定为 3 分钟，没有使用剩余路线的实际增量时间。
4. 算法只比较等待、绕行、稳定性和利用率的加权总分，没有把“额外启用一辆车”作为优先级更高的运营成本。
5. 候选评估和任务节点写入使用不同逻辑，除同站点上车外，实际插单仍可能把节点追加到任务末尾。

因此，新车候选天然获得较高稳定性分数，路线可行的既有任务反而可能落选。

## 2. 目标

后续订单调度采用以下已确认规则：

> 在新乘客等待不超过 5 分钟、所有乘客额外绕行不超过 8 分钟、车辆容量充足且节点顺序可执行时，优先插入已有车辆任务；只有不存在可行插单方案时才启用新车。

具体目标：

1. 优先复用 `DISPATCHED` 或 `IN_PROGRESS` 的可插单任务。
2. 基于真实剩余路线判定合乘，不再依赖站点是否已存在于原任务。
3. 使用路线增量计算等待时间、乘客绕行和到站时间。
4. 按路线分段校验在车人数，而不是把任务关联订单人数简单累加。
5. 自动派单和人工复核共用同一插单规划与节点落地逻辑。
6. 在决策解释和审计中记录车辆启用成本、插单指标及最终选择原因。

## 3. 非目标

本轮不包含：

- 设置订单聚合等待窗口；
- 对一批未调度订单执行全局车辆路径优化；
- 修改 5/8/60 分钟规则、82/62 阈值或 0.35/0.20/0.30/0.15 权重；
- 修改已发车任务或重算历史调度决策；
- 增加可配置的货币成本、油耗或司机工时计费模型；
- 调整乘客端、司机端或运营看板。

车辆启用成本在本轮表示为离散运营成本：复用已有任务为 `0`，新建车辆任务为 `1`。

## 4. 方案选择

采用“路线感知的增量插单”方案：保持订单逐笔实时调度，但在每次调度时枚举既有任务的合法插入位置，优先选择可行的既有任务；只有既有任务全部不可行时，才比较新车候选。

没有采用仅增加评分惩罚的方案，因为有限惩罚仍可能让新车候选获胜，不能严格落实“可合乘时优先合乘”。没有采用滚动批量全局优化，因为它会改变即时订单响应时间，并引入批量调度、并发重算和更大范围的运营规则。

## 5. 总体架构

### 5.1 `TaskInsertionPlanner`

在 API 服务的调度领域新增统一插单规划器，输入：

- 待调度订单；
- 候选车辆及最新位置快照；
- 候选车辆任务和剩余任务节点；
- 虚拟站点坐标；
- 当前启用的调度规则。

输出 `TaskInsertionPlan`：

- 是否可行；
- 上车和下车的插入位置；
- 调整后的剩余节点顺序及预计到站时间；
- 新乘客预计等待时间；
- 所有乘客最大额外绕行时间；
- 插单后的峰值在车人数和利用率；
- 路线是否降级及降级原因；
- 不可行时的首要拒绝原因。

规划器是既有任务插单判断的唯一来源，候选组装、自动派单和人工复核不得各自实现另一套顺序规则。

### 5.2 候选组装

`CandidateTaskAssembler` 继续生成两类候选，但补充候选类型和启用成本：

- `EXISTING_TASK`：`activationCost = 0`；指标来自 `TaskInsertionPlanner`。
- `NEW_TASK`：`activationCost = 1`；路线为车辆当前位置 → 上车点 → 下车点。

组装结果保留从任务 ID 到 `TaskInsertionPlan` 的映射。自动派单选中既有任务后，必须在任务锁内使用同一个规划器重新校验，并以重新校验得到的规划结果写入节点，避免评估结果与实际落地发生偏差。

### 5.3 算法服务

算法合同增加：

- `candidateType`：`EXISTING_TASK` 或 `NEW_TASK`；
- `activationCost`：本轮只允许 `0` 或 `1`；
- 路线感知的等待、最大乘客绕行、任务扰动和利用率指标。

候选选择改为两级排序：

1. 先执行容量、等待、绕行、路线可用性和节点顺序约束过滤。
2. 若存在可行的 `EXISTING_TASK`，只在这些候选中按现有加权评分选最优方案。
3. 只有不存在可行既有任务时，才在 `NEW_TASK` 候选中按现有加权评分选最优方案。

该规则等价于先最小化车辆启用成本，再优化服务质量和任务稳定性。评分阈值仍决定自动派单、人工复核或不可服务，不因优先合乘而绕过 82/62 阈值。

### 5.4 任务节点落地

扩展现有 `TaskStopInsertionPolicy`，使其接受规划器给出的目标顺序，而不是仅处理同站点上车后把下车节点追加到末尾。

节点落地必须保证：

- 已完成或已越过的历史节点顺序不变；
- 新订单上车节点早于其下车节点；
- 相邻同站点上车节点继续保持分组，以兼容已经验收的同站点联动；
- 所有剩余节点连续重新编号；
- 每个订单仍分别确认上车、下车并分别写入审计。

## 6. 路线与约束计算

### 6.1 基线剩余路线

对既有任务，以车辆最新位置快照为起点，仅保留尚未执行完成的节点，计算基线剩余路线及各节点预计到达时间。已完成、已取消或已经越过的节点不能参与重排。

若车辆没有位置快照，沿用现有 `VEHICLE_LOCATION_SNAPSHOT_MISSING` 保护。若地图路线服务降级，则保留 `MAP_ROUTE_UNAVAILABLE` 人工复核保护，不使用直线估算自动派单。

### 6.2 插入位置枚举

在未完成节点的边界上枚举：

- 上车节点插入位置 `i`；
- 下车节点插入位置 `j`，且 `j > i`。

同站点已有可执行上车节点时，新上车节点优先插入该连续分组末尾。其他情况按路线增量选择最优位置。任何需要返回已完成站点或破坏已发生事件顺序的方案直接拒绝。

### 6.3 等待时间

新乘客等待时间定义为：

`max(0, 规划后到达上车点时间 - 订单期望出发时间)`

超过规则组 `maxWaitMinutes` 的候选以 `WAIT_TIME_EXCEEDED` 拒绝。

### 6.4 乘客额外绕行

额外绕行按乘客承诺分别计算：

- 对既有乘客，比较插单前后其下车节点预计到达时间；
- 对新乘客，比较规划内乘车时间与上车点到下车点的直接路线时间。

候选的 `estimatedDetourMinutes` 取所有受影响乘客中的最大正向增量。超过 `maxDetourMinutes` 的候选以 `DETOUR_TIME_EXCEEDED` 拒绝。

该口径避免用总路线增量掩盖某一名乘客受到的较大延误。

### 6.5 分段容量

规划器从车辆当前在车人数开始，按调整后的剩余节点依次计算：

- `BOARDING`：增加该订单人数；
- `ALIGHTING`：减少该订单人数；
- 已上车但尚未下车的订单计入初始在车人数；
- 已取消订单不计入。

任一分段人数超过车辆容量，候选以 `INSUFFICIENT_CAPACITY` 拒绝。算法合同中的 `utilizationAfterInsert` 使用规划后的峰值在车人数除以车辆容量。

## 7. 稳定性与合乘判定

既有逻辑通过“新订单上下车站是否已存在”判断同向，必须替换为路线规划结果：

- 存在合法插入顺序且满足等待、绕行和容量约束，视为可合乘；
- 任务扰动根据最大乘客延误和受影响的未完成节点数量计算；
- `SAME_DIRECTION_ONLY` 策略仍可使用路线是否需要明显折返作为附加约束；
- 当前试点的 `REALTIME_INSERTION` 映射为灵活插单，但仍必须通过 5/8 分钟硬约束。

新任务没有既有乘客扰动，但其车辆启用成本为 `1`，不会在存在可行既有任务时仅凭稳定性高分胜出。

## 8. 自动派单与人工复核一致性

### 8.1 自动派单

自动派单选中既有任务后：

1. 在事务内锁定任务并刷新状态；
2. 用统一规划器根据最新任务状态重新校验；
3. 校验通过后按规划顺序写入节点；
4. 校验失败时回滚本次调度，返回 `DISPATCH_CANDIDATE_STALE`，订单保持可重新调度状态。

系统不得在候选过期后静默启用另一辆车。

### 8.2 人工复核

人工复核决策继续持久化最佳车辆和最佳任务。调度员确认时：

1. 锁定候选任务；
2. 使用当前任务状态重新计算同一车辆任务的插单方案；
3. 若仍满足约束则写入；
4. 若不再满足约束则拒绝确认并提示重新调度，人工复核条目保持未确认。

这样无需长期保存可能过期的节点序号，同时保证人工确认不会使用陈旧路线。

## 9. 决策解释与审计

调度决策解释增加以下字段：

- `candidateType`；
- `activationCost`；
- `selectionReason`：`EXISTING_TASK_PREFERRED` 或 `NEW_VEHICLE_REQUIRED`；
- `baselineRouteDurationSeconds`；
- `plannedRouteDurationSeconds`；
- `estimatedWaitMinutes`；
- `maxPassengerDetourMinutes`；
- `peakOccupiedSeats`；
- `insertionBoardingPosition` 和 `insertionAlightingPosition`；
- 路线提供方和降级信息。

审计记录只保存订单、任务、车辆和决策标识及上述运营指标，不保存乘客电话。

## 10. 错误处理

新增或明确以下运营原因：

- `NO_FEASIBLE_EXISTING_TASK`：没有满足约束的既有任务，允许继续评估新车；
- `DISPATCH_CANDIDATE_STALE`：应用决策前任务已变化，需要重新调度；
- `ROUTE_INSERTION_UNAVAILABLE`：无法构造合法节点顺序；
- 继续复用 `WAIT_TIME_EXCEEDED`、`DETOUR_TIME_EXCEEDED`、`INSUFFICIENT_CAPACITY`、`MAP_ROUTE_UNAVAILABLE` 和 `VEHICLE_LOCATION_SNAPSHOT_MISSING`。

当既有任务不可行但新车可行时，订单正常使用新车，不显示为不可服务；决策解释必须说明启用新车的首要原因。

## 11. 测试先行范围

实施必须先写失败测试，再写实现代码。

### 11.1 插单规划器单元测试

- 枚举多站点合法插入顺序并选择最小乘客绕行方案；
- 同站点上车保持连续分组；
- 不允许插回已完成站点；
- 等待恰好 5 分钟通过，超过 5 分钟拒绝；
- 最大额外绕行恰好 8 分钟通过，超过 8 分钟拒绝；
- 分段峰值等于容量通过，超过容量拒绝；
- 已上车乘客正确计入初始占用。

### 11.2 算法服务测试

- 可行既有任务评分低于新车时，仍选择既有任务；
- 多个可行既有任务按现有权重选最高分；
- 没有可行既有任务时选择新车；
- 所有候选不满足阈值时保持人工复核或不可服务；
- 解释中包含候选类型、启用成本和选择原因。

### 11.3 API 编排测试

- 自动派单复用既有任务，不重复占用车辆和驾驶员；
- 人工复核确认使用同一规划器；
- 任务在评估后变化时拒绝陈旧方案并回滚；
- 自动与人工路径产生相同节点顺序；
- 现有同站点多人上车、任务锁和审计测试继续通过。

### 11.4 三单回归场景

按小袁、高士、刘小光的线路和顺序逐笔调度，使用受控路线数据使该场景客观满足 5 分钟等待和 8 分钟绕行约束，并准备一辆已有任务车辆和其他空闲车辆，断言：

- 三笔订单最终关联同一个车辆任务和同一辆 8 座车；
- 陇阳镇两笔上车节点连续；
- 安川上车以及中医院、姜滩小学、高铁站下车顺序由最小绕行计算确定且可执行；
- 峰值在车人数为 4；
- 每笔订单等待不超过 5 分钟；
- 每名乘客额外绕行不超过 8 分钟；
- 第二、第三笔决策的 `activationCost` 为 `0`；
- 不创建第二、第三个车辆任务。

## 12. 部署与验收

1. 先运行插单规划器、算法、API 编排和任务执行相关测试。
2. 再运行 API 与算法完整测试、管理端测试和生产构建。
3. 算法合同版本从 `0.1.0` 升级到 `0.2.0`，API 与算法服务必须同时部署。
4. 部署只影响部署后的新调度请求，不重算已确认、已发车或执行中的历史订单。
5. 选择无活动测试任务的窗口重启本地 API 和算法服务。
6. 浏览器验收使用新建模拟订单；任何真实订单调度、人工复核或任务节点操作仍需单独授权。

验收通过标准：满足硬约束的既有任务始终优先于新车；不可合乘时仍能正常启用新车；自动派单、人工复核和任务执行的节点顺序一致，且既有回归测试全部通过。
