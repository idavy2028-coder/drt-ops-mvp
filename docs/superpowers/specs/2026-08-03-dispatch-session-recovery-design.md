# 调度工作台会话恢复设计

## 背景与根因

`dispatcher02` 在人工复核队列点击“确认派单”后收到“登录状态已失效，请重新登录”。数据库确认该次操作没有生成刘盛美订单的确认派单决策，订单仍为 `PENDING_MANUAL_REVIEW`；同时，同一账号随后能执行车辆任务操作，说明账号、角色和后端权限配置有效。

前端调度页的“刷新”只调用 `loadWorkbench()` 拉取业务数据：它不会清除 `actionError`，也不会主动恢复内存中的访问令牌。完整页面重载后会通过刷新令牌建立新会话，因此原提示消失。当前 HTTP 客户端仅在业务请求已收到 401 后尝试一次刷新，人工复核操作没有在动作开始前确保内存会话有效，且失败消息会留在队列面板中。

## 方案

采用最小前端修复，不改变后端权限、订单状态机、派单算法或任何业务数据。

1. 为人工确认和人工拒绝抽取一个受保护的操作入口：操作开始时先调用 `authStore.restore()`。
2. 会话可恢复时，再调用原有确认或拒绝 API；请求层仍保留既有的 401 后刷新并重试，形成两层保护。
3. 会话不可恢复时，不发送派单请求，显示“登录状态已失效，请重新登录”，并保留人工复核条目。
4. 点击工作台“刷新”时清除已完成操作的历史错误；若刷新本身失败，仍用页面级 `status` 显示加载错误，避免混入人工复核操作错误。

## 测试与验收

先添加并运行以下失败测试：

- 访问令牌缺失但 `restore()` 成功时，点击“确认派单”会在 API 调用前恢复会话并完成确认。
- `restore()` 失败时，不调用确认 API，显示登录失效提示，复核条目仍可见。
- 先发生一次人工确认错误后，点击“刷新”会移除旧错误提示。

实现后运行调度页单测、管理端完整测试和生产构建；再重启本地前端容器。浏览器验收仅在用户再次明确授权后，对刘盛美这一条订单点击一次“确认派单”，核对订单状态、人工复核队列和生成的车辆任务。

## 非目标与安全边界

- 不改变 `dispatcher02` 的角色或权限。
- 不修改刷新令牌、账号、订单、决策或车辆任务数据。
- 不自动提交人工复核；浏览器中的确认派单仍需单独授权。
