# P1-4 算法不可用错误映射设计

**日期：** 2026-07-29
**对应任务：** P1-4「验证算法服务运行依赖」

## 1. 目标

当 API 调用算法服务失败、超时或收到不可用响应时，调度接口返回可稳定识别的 HTTP 503 业务错误；管理页面显示“算法服务不可用”，且不得显示“登录状态已失效，请重新登录”。

本任务同时创建一笔专用于 P1-4 断路验收的即时测试订单。算法不可用时的调度请求必须回滚，不改变订单状态，不生成调度决策、车辆任务或调度审计。恢复算法后保留该订单为 `PENDING_DISPATCH`，等待用户确认后再进入 P1-5。

本任务不修复重复点击或并发调度问题，不执行成功调度，不提交、推送或创建 PR。

## 2. 已确认根因

错误链路存在两个缺口：

1. `WebClientAlgorithmClient` 直接向上传播连接失败、上游 HTTP 错误、响应解析错误和阻塞超时。API 无法把这些异常识别为算法服务故障，只能产生通用服务端错误。
2. 前端 `apiErrorFromResponse` 只提取 HTTP 400 和 409 的业务文案。该限制可以避免把数据库异常等 5xx 技术信息显示给用户，但也意味着普通 503 响应无法传递算法专用文案。

因此，单独修改后端文案或单独修改页面都不能同时满足“准确区分算法故障”和“不泄露其他服务端错误”两个要求。

## 3. 方案选择

采用“后端稳定错误码 + 前端白名单映射”方案：

- 算法客户端把调用边界内的运行时失败转换为专用 `AlgorithmUnavailableException`，保留原异常作为服务端诊断原因，但不向响应暴露技术细节。
- 全局异常处理器将该异常转换为 HTTP 503，响应数据包含稳定错误码 `ALGORITHM_UNAVAILABLE` 和文案“算法服务不可用”。
- 前端只对白名单错误码 `ALGORITHM_UNAVAILABLE` 使用专用文案；无错误码或未知错误码的 5xx 仍显示“服务暂时不可用，请稍后重试”。
- HTTP 401 的刷新与登录失效逻辑保持不变，算法故障不会触发令牌刷新或登录失效提示。

不采用以下方案：

- 所有 503 都显示“算法服务不可用”：会把数据库、反向代理或其他上游故障误报为算法故障。
- 页面把所有 500/503 直接改成算法文案：无法表达真实故障来源，并削弱通用错误保护。
- 直接信任所有 5xx 响应中的 `message`：可能把服务端技术异常泄露到页面。

## 4. 文件边界

计划新增或修改以下文件：

- `apps/api/src/main/java/com/idavy/drtops/integration/algorithm/AlgorithmUnavailableException.java`：算法调用边界的专用异常。
- `apps/api/src/main/java/com/idavy/drtops/integration/algorithm/WebClientAlgorithmClient.java`：捕获算法调用失败并转换专用异常。
- `apps/api/src/main/java/com/idavy/drtops/common/GlobalExceptionHandler.java`：返回带稳定错误码的 HTTP 503。
- `apps/api/src/test/java/com/idavy/drtops/integration/algorithm/WebClientAlgorithmClientTest.java`：验证连接失败被安全转换。
- `apps/api/src/test/java/com/idavy/drtops/common/GlobalExceptionHandlerTest.java`：验证 503、错误码和安全文案。
- `apps/admin-web/src/api/errors.ts`：解析安全错误码并映射用户文案。
- `apps/admin-web/src/api/errors.test.ts`：验证白名单 503 与普通 5xx 的不同处理。
- `apps/admin-web/src/pages/orders-page.test.ts`：验证调度失败时页面显示算法不可用且不误报登录失效。

不修改订单、调度决策或审计领域模型，不新增数据库迁移。

## 5. 运行时数据流

1. 调度员在订单页面点击专用测试订单的“调度”。
2. API 进入现有事务并组装候选方案。
3. `WebClientAlgorithmClient` 调用算法 `/dispatch/evaluate`。
4. 算法连接失败、超时、返回非成功状态或响应不可解析时，客户端抛出 `AlgorithmUnavailableException`。
5. 异常退出调度事务，已加载或临时变更的业务状态回滚。
6. 全局异常处理器返回 HTTP 503：

   ```json
   {
     "data": {
       "code": "ALGORITHM_UNAVAILABLE",
       "message": "算法服务不可用"
     }
   }
   ```

7. 前端识别白名单错误码，在页面状态区和错误反馈中显示“算法服务不可用”。
8. 因响应不是 401，前端不会触发登录刷新失败流程，也不会显示登录失效。

## 6. 错误边界

算法适配器负责把以下调用边界故障统一视为服务不可用：

- DNS、连接拒绝、连接重置等网络错误；
- WebClient 上游 4xx/5xx 响应；
- 五秒阻塞等待超时；
- 算法响应反序列化失败或空响应。

专用异常对客户端只暴露固定错误码和固定中文文案。原始异常保留在异常链中，供服务端日志和调试使用。

订单状态不合法、规则组缺失、候选数据冲突等既有领域错误不在算法客户端边界内，继续使用原有 4xx 或 5xx 映射。

## 7. 测试策略

严格采用测试驱动开发：

1. 先新增算法客户端失败转换测试，确认现有实现暴露原始 WebClient 异常。
2. 先新增全局异常响应测试，确认现有处理器不支持算法专用错误码。
3. 先新增前端错误解析测试，确认现有实现把带错误码的 503 显示为通用服务错误。
4. 先新增订单页面测试，模拟列表中存在 `PENDING_DISPATCH` 订单，点击调度后收到专用 503，确认页面当前不能显示目标文案。
5. 完成最小实现后，分别运行定向后端和前端测试，再运行后端全量测试、前端类型检查、全量 Vitest 和生产构建。

前端测试还必须证明：

- `ALGORITHM_UNAVAILABLE` 显示“算法服务不可用”；
- 未标记的 500/503 技术文案不会透传；
- 页面不出现“登录状态已失效，请重新登录”。

## 8. 真实环境验收

### 8.1 基线

- 从 API 容器访问算法 `/health`，结果为 `{"status":"UP"}`。
- API Actuator 健康端点返回 HTTP 200。
- 通过后台页面创建一笔名称明确包含 `P1-4` 的即时测试订单，使用虚构测试姓名和电话、现有启用站点及 GCJ-02 坐标。
- 只读记录订单 ID、初始状态以及关联决策、任务、审计数量。

### 8.2 断路验证

- 在订单页定位该订单并确认“调度”按钮可用。
- 停止且只停止算法容器。
- 从 API 容器确认算法 `/health` 无法访问。
- 单击一次该订单的“调度”，确认页面显示“算法服务不可用”，且不显示登录失效。
- 无论页面验证成功或失败，都立即重新启动算法容器并按健康条件轮询，不使用固定等待替代健康检查。

### 8.3 恢复与副作用核查

- 从 API 容器再次确认算法 `/health` 为 `UP`，API Actuator 返回 HTTP 200。
- 只读验证测试订单仍为 `PENDING_DISPATCH`。
- 只读验证该订单没有新增调度决策、车辆任务或调度审计。
- 保留测试订单，不在本任务中再次点击调度；后续是否作为 P1-5 样本由用户审阅后决定。

不停止数据库、Redis、API 或前端容器，不删除任何容器或数据卷。

## 9. 完成标准

满足以下全部条件才可认定 P1-4 收口：

- API 容器内可访问算法 `/health`。
- 算法不可用时调度接口返回 HTTP 503 和 `ALGORITHM_UNAVAILABLE`。
- 页面显示“算法服务不可用”，且不显示登录失效。
- 普通未知 5xx 仍显示通用服务错误，不泄露技术信息。
- 断路调度事务没有改变测试订单状态，也没有新增决策、任务或调度审计。
- 算法和 API 在验收后恢复健康。
- 定向与全量自动化验证通过。
- 未执行 P1-5 的成功调度，未提交或推送变更。
