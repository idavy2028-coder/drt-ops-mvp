# 乘客取消时释放任务资源设计

## 目标

当已确认订单因乘客取消而关闭时，系统应准确处理关联车辆任务：仅承载该订单的任务同步取消并释放车辆、驾驶员；仍承载其他有效订单的拼载任务仅取消该订单站点，继续运行。

## 范围与约束

- 使用现有订单取消入口，取消原因记录为“乘客取消”。
- 不使用“车辆故障”或“严重延误”接口替代乘客取消。
- 保留订单 `CANCELLED` 终态；任务状态按实际资源处置分别为 `CANCELLED` 或保持活动状态。
- 不修改数据库结构、派单规则、算法参数或位置事件格式。
- 仅处理取消时仍处于活跃状态的关联任务；无关联活跃任务时维持现有取消行为。
- 所有资源释放必须经 `TaskResourceCoordinator.releaseIfUnused`，避免释放仍被其他活动任务占用的车辆或驾驶员。

## 流程

1. 订单取消服务锁定并取消订单，写入 `ORDER_CANCELLED` 审计记录，原因为“乘客取消”。
2. 查询该订单关联的活跃车辆任务。
3. 对每个关联任务判断 `activeOrderIds()`：
   - 若仅包含当前订单：取消该订单的未完成站点，取消任务，调用资源协调器释放车辆和驾驶员，写入 `TASK_CANCELLED_PASSENGER_CANCELLED` 审计记录。
   - 若包含其他有效订单：仅取消当前订单的未完成站点，不取消任务、不释放资源，写入 `TASK_STOPS_CANCELLED_PASSENGER_CANCELLED` 审计记录。
4. 事务提交后，订单、任务、车辆与驾驶员状态一致可审计。

## 错误处理

- 已终态订单沿用领域对象现有的状态机保护，拒绝重复取消。
- 资源释放只在任务已取消且同车辆/驾驶员不存在其他活跃任务时生效。
- 任务或订单不存在时保持现有的 404 行为。

## 验收标准

- 单订单任务的乘客取消使订单与任务均取消，车辆和驾驶员恢复可调度/空闲。
- 拼载任务的乘客取消不影响其他订单的站点、任务状态或资源占用。
- 两种路径都包含“乘客取消”的审计原因，且不产生车辆故障或严重延误审计。
