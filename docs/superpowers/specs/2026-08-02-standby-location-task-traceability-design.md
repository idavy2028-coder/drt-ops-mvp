# 待命位置上报与任务追溯整改设计

日期：2026-08-02
状态：已确认方案 A，待设计文档复核

## 1. 背景与问题

试运行中发现，“位置历史”页面的“待命位置上报”允许选择 `DISPATCHED` 车辆。该动作实际写入车辆级 `MANUAL_REPORT`，请求明确不关联车辆任务和任务节点，因此上报后只会更新车辆最新位置，不会生成或改变任务编号，也无法从该事件获取客户订单信息。

当前行为同时存在以下风险：

1. 页面将所有车辆列为“待命车辆”，容易让运营人员对已派单或执行中的车辆误报待命位置。
2. 前端即使增加过滤，旧页面或直接请求仍可能绕过限制。
3. “任务编号”输入框没有说明它只是筛选条件，容易被误认为系统会自动回填。
4. 位置事件虽然已有 `vehicleTaskId`，页面没有展示任务短编号或跳转入口，任务追溯割裂。
5. 位置历史不应扩展为客户信息页面，乘客姓名和联系方式必须继续留在订单中心的授权边界内。

## 2. 目标

- 只有当前状态为 `IDLE` 的车辆可以进入待命位置上报候选列表。
- 后端在写入前重新检查车辆状态；非 `IDLE` 车辆提交待命位置时返回 HTTP 409，且不产生位置事件或最新位置变化。
- 位置历史明确区分“任务关联事件”和“无任务关联的待命上报”。
- 有任务关联的事件显示任务短编号，并可进入车辆任务页定位该任务。
- “任务编号”明确标记为筛选条件。
- 不在位置历史展示乘客姓名、电话或其他客户隐私字段。

## 3. 非目标

- 不新增驾驶员端 App 或驾驶员接单页面。
- 不把待命位置上报改造成任务动作。
- 不在位置历史聚合或展示订单详情。
- 不改变发车、到站、上下车、完成等现有任务状态机。
- 不自动修正历史上已经存在的无任务关联位置事件。

## 4. 方案选择

采用方案 A：前后端双重约束，并补充任务追溯入口。

只做前端过滤无法防止旧页面和直接请求绕过；把待命上报整体迁移到任务页则会破坏无任务车辆的位置校准场景。方案 A 在保持现有职责边界的前提下提供完整防护。

## 5. 后端设计

### 5.1 待命车辆候选

`VehicleLocationQueryService.reportableVehicles()` 只返回 `currentStatus == IDLE` 的车辆。`dispatchable` 字段继续保留，用于页面说明和未来校准流程；本次不要求 `dispatchable=true`，因为空闲但暂不可调度的车辆仍可能需要先校准位置。

### 5.2 写入防绕过

车辆级位置上报服务在处理 `MANUAL_REPORT` 且 `vehicleTaskId == null`、`taskStopId == null` 的待命上报时，必须读取并锁定目标车辆，然后验证状态为 `IDLE`。不满足时返回 HTTP 409，错误信息统一为：

> 当前车辆正在执行或等待任务，不能上报待命位置

拒绝请求不得创建位置事件、不得推进最新位置快照，也不得改变车辆或任务状态。

普通任务动作继续走既有任务执行接口，不受本规则影响。管理员位置修正继续走既有修正语义，不被误判为待命上报。

### 5.3 并发一致性

状态检查与位置事件写入必须处于同一事务。若车辆在候选列表加载后被派单，写入时的后端检查仍应拒绝待命上报。实现优先复用车辆仓储的悲观锁读取；如当前仓储没有对应接口，则增加仅供命令服务使用的锁定查询。

## 6. 前端设计

### 6.1 待命候选与错误反馈

- 页面只渲染后端返回的 `IDLE` 候选。
- 候选加载后如没有空闲车辆，显示“当前没有可上报待命位置的空闲车辆”。
- 后端 409 使用统一业务错误文案展示，保留表单内容，方便运营人员核对后关闭。
- 下拉标题仍为“待命车辆”，每项继续显示车牌、状态和是否可调度。

### 6.2 筛选条件文案

将位置历史筛选区的标签从“任务编号”改为“任务编号（筛选条件）”。占位提示改为“输入完整任务编号”，避免将其理解为上报结果字段。

### 6.3 事件任务关联

- `vehicleTaskId` 非空：在事件时间线显示 `任务 <前 8 位>` 和“查看任务”链接。
- `vehicleTaskId` 为空：显示“无任务关联”，明确待命位置不会生成任务。
- 链接目标为 `/tasks?taskId=<完整 UUID>`。
- 不增加订单编号、乘客姓名、乘客电话等字段。

### 6.4 任务页定位

车辆任务页读取 URL 查询参数 `taskId`：

- 若参数匹配已加载任务，自动选择该任务并展示对应站点时间线与可用动作。
- 参数不存在、格式无效或任务不在当前列表时，不报错、不选择错误任务，并保留当前默认行为。
- 用户后续手工选择其他任务时正常覆盖 URL 初始选择，不强制锁定。

## 7. 数据流

### 7.1 待命位置上报

1. 前端请求待命候选。
2. 后端仅返回 `IDLE` 车辆。
3. 操作员选择车辆并提交位置。
4. 后端在事务内重新锁定并校验车辆状态。
5. 校验通过后写入无任务关联的 `MANUAL_REPORT`；校验失败返回 409，不写数据。
6. 前端刷新候选，并按车辆编号查询位置历史。

### 7.2 任务追溯

1. 位置历史读取事件已有的 `vehicleTaskId`。
2. 页面显示任务短编号和“查看任务”。
3. 用户进入 `/tasks?taskId=<UUID>`。
4. 任务页加载完成后按完整 UUID 自动选中任务。

## 8. 错误处理与安全边界

- 车辆状态冲突使用 HTTP 409，而不是 400 或 500。
- 状态冲突不重试、不自动改为任务位置事件。
- 无效 `taskId` 查询参数不触发额外请求或异常提示。
- 页面只展示任务标识，不展示客户个人信息。
- 本次不改变现有角色权限：`LOCATION_REPORT` 控制待命上报，任务和位置读取继续使用原权限。

## 9. 测试策略

严格采用测试先行，每项生产代码变更前先运行对应失败测试并确认失败原因。

### 9.1 后端

- 候选查询测试：`IDLE` 被返回，`DISPATCHED`、`IN_PROGRESS`、`OFFLINE` 不返回。
- 命令服务测试：非 `IDLE` 车辆的待命上报返回状态冲突。
- 集成测试：409 请求不创建位置事件、不推进快照、不改变车辆和任务状态。
- 回归测试：`IDLE` 车辆仍可成功上报；任务动作和管理员修正不受影响。

### 9.2 前端

- API/页面测试：候选列表只展示后端返回的空闲车辆，空列表显示明确提示。
- 页面测试：任务编号标签和占位提示明确为筛选条件。
- 时间线测试：有任务 ID 显示短编号和任务链接；无任务 ID 显示“无任务关联”。
- 任务页测试：有效 `taskId` 自动选中；无效或不存在的 `taskId` 不误选。
- 错误处理测试：409 文案展示且表单不关闭。

### 9.3 验收

- 前后端相关测试、全量测试、类型检查和生产构建通过。
- 部署至本地试点环境后，用 `SYSTEM_ADMIN` 或具备相应权限的调度账号完成浏览器验收：
  1. 待命候选中不出现已派单车辆；
  2. 模拟状态竞争时后端返回 409；
  3. 无任务待命事件显示“无任务关联”；
  4. 任务事件可跳转并定位对应任务；
  5. 页面不显示乘客隐私字段。

## 10. 发布与回滚

- 本次不涉及数据库迁移。
- 先部署 API，再部署前端，避免新前端依赖未上线的防绕过行为。
- 回滚时可独立回滚前端；后端状态校验属于安全收紧，除非确认影响合法 `IDLE` 上报，否则不建议回滚。

## 11. 完成标准

- 已派单或执行中车辆无法通过页面或接口上报待命位置。
- 空闲车辆待命位置上报保持可用。
- 位置历史清晰显示任务关联状态，并可定位任务。
- 任务筛选字段不再被误解为自动回填字段。
- 未扩大客户信息可见范围。
