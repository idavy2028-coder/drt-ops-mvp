# 同站点多人上车与插单排序设计

## 背景

试运行任务 `1626d98d` 承载两笔订单。两笔订单的上车虚拟站点均为“高铁站”，但第二笔订单经人工复核插入既有任务时，其上车、下车节点被直接追加到任务末尾，形成以下错误序列：

1. 第一笔高铁站上车；
2. 第一笔安川下车；
3. 第二笔返回高铁站上车；
4. 第二笔陇阳镇下车。

现场实际为两名乘客在同一次高铁站停靠中上车。现有序列既不符合实际行驶过程，也导致车辆任务页面无法在当前站点记录第二笔订单上车。

## 目标

- 新订单插入既有任务时，若其上车虚拟站点与任务中未结束的上车节点相同，则将新上车节点插入同站点节点组内，而不是追加到已有下车节点之后。
- 同一物理停靠中的相邻同站点上车节点共享一次到站事实和位置事件。
- 每笔订单仍独立确认上车，分别保留乘客上车审计，支持单独处理乘客未到。
- 自动派单和人工复核使用同一套任务节点插入策略。
- 不修改现有数据库表结构，不把多笔订单合并成单个 `TaskStop`。
- 安全纠正当前试运行任务，保留完整的人工纠正审计和纠正前备份。

## 非目标

- 不重写通用路径规划算法，也不在本次设计中实现所有可能的上下车组合优化。
- 不允许驾驶员任意跳过不同站点或越序操作。
- 不批量确认同站点全部乘客上车。
- 不修改服务区、虚拟站点、车辆容量、派单评分阈值或路线供应商配置。
- 不为单次历史数据纠正增加长期暴露的管理端接口。

## 方案选择

采用方案 A：保留“一笔订单一个上车节点、一个下车节点”的数据模型，增加统一的同站点插入策略和到站联动。

未采用的方案：

- 将多笔订单合并为一个物理停靠实体：需要数据库迁移、接口和页面重构，超出当前试运行缺陷修复范围。
- 仅放开前端越序操作：会保留错误任务序列，并允许绕过后端业务顺序，不能接受。

## 任务节点插入规则

### 同站点上车

插入新订单时，统一插入策略按任务当前节点序列查找与新订单 `boardingStopId` 相同的上车节点。

匹配节点必须满足：

- `stopType` 为 `BOARDING`；
- `virtualStopId` 与新订单上车站点相同；
- 节点未取消；
- 节点所属任务仍为 `DISPATCHED` 或 `IN_PROGRESS`；
- 匹配位置不会把新上车节点插到已经离开的不同站点之前。

找到匹配节点时，新上车节点插在同站点连续节点组的末尾；新订单下车节点保留在原任务后续节点之后。插入完成后，对全部任务节点重新生成连续且唯一的 `sequenceNumber`。

对于本次任务，目标顺序为：

1. 第一笔高铁站上车；
2. 第二笔高铁站上车；
3. 第一笔安川下车；
4. 第二笔陇阳镇下车。

### 不同站点上车

未找到可复用的同站点上车节点时，维持当前末尾追加行为：新上车节点和新下车节点依次追加到任务末尾。本次修复不尝试计算任意中间插入位置。

### 已离开站点

若任务已经完成该站点的全部节点且当前执行位置已推进到后续不同站点，则不得把新订单插回历史站点。候选任务应继续按现有评分和人工复核规则处理，不能通过重排制造虚假的返回停靠。

## 共享到站与逐单上车

### 到站联动

驾驶员对当前上车节点执行“到站”时，后端从该节点开始检查连续的同站点上车节点。满足以下条件的节点共享本次到站：

- `virtualStopId` 相同；
- `stopType` 均为 `BOARDING`；
- 状态为 `PLANNED`；
- 节点在序列中连续，中间没有不同站点或下车节点。

符合条件的节点同时进入 `ARRIVED`，使用同一个位置事件和同一个实际到站时间。每个被联动的任务节点分别写入 `TASK_STOP_ARRIVED` 审计，审计元数据引用同一个位置事件，从而既表达“一次物理到站”，又能逐订单追溯。

不同站点、非连续节点或非 `PLANNED` 节点不得被联动。

### 逐单上车

“上车”操作仍只处理一个 `ARRIVED` 上车节点：

- 每点击一次，只把一笔订单对应的节点改为 `BOARDED`；
- 每笔订单分别生成 `PASSENGER_BOARDED` 位置事件和审计；
- 当前节点完成后，页面继续提供下一个同站点 `ARRIVED` 节点的“上车”操作；
- 某笔订单的乘客未到时，其他订单仍可正常上车，该订单可独立进入 5 分钟乘客未出现流程。

## 代码结构

### 统一插入策略

新增一个领域级任务节点插入组件，职责仅限于：

- 接收既有 `VehicleTask`、新订单上车节点和下车节点；
- 决定同站点相邻插入或末尾追加；
- 重新生成连续序号；
- 返回或直接更新任务节点集合。

`DispatchOrchestrator` 和 `ManualReviewService` 必须共同调用该组件，不再分别计算 `max(sequenceNumber) + 1`。

### 任务领域对象

`VehicleTask` 提供受控的节点重排能力，禁止调用方直接修改只读节点列表。重排必须保持：

- 节点 ID、订单 ID、虚拟站点 ID、计划时间和执行状态不变；
- 序号从 1 开始连续递增；
- 每个任务内序号唯一；
- 已完成节点的相对顺序不被破坏。

### 到站执行服务

`TaskExecutionService.arrive` 在验证当前任务和触发节点后，计算连续同站点上车节点组，使用一个位置上报结果更新节点状态，并为每个受影响节点写入到站审计。

前端继续使用“首个 `PLANNED` 节点到站”和“首个 `ARRIVED` 上车节点上车”的顺序模型。后端联动后，页面会依次暴露同站点乘客的逐单上车按钮，不需要开放任意节点选择。

## 并发与错误处理

- 插单和任务执行继续使用现有任务执行锁读取任务，避免人工复核、自动派单和驾驶员操作同时改写节点。
- 插入前再次验证任务状态、车辆一致性和容量；任何条件变化均返回冲突，不写入部分节点。
- 到站联动仅在触发节点仍为 `PLANNED` 时执行；重复请求继续使用现有位置事件幂等机制。
- 重排后若序号不连续、出现重复或破坏已完成节点顺序，事务必须失败并回滚。
- 同站点联动中的任一节点更新失败时，全部节点状态和审计一起回滚。

## 测试策略

严格遵循 RED-GREEN-REFACTOR：先写测试并观察预期失败，再编写最小实现。

### 插入策略单元测试

- 新订单上车站与既有上车站相同时，新上车节点位于既有同站点上车节点之后、原下车节点之前。
- 同站点存在两个连续上车节点时，新节点追加到该连续组末尾。
- 上车站不同时，仍按末尾追加上车和下车节点。
- 已离开的历史同站点不得被重新插入。
- 重排后序号从 1 开始连续且唯一，节点其他字段保持不变。

### 派单服务测试

- 自动派单插入既有任务时使用统一策略。
- 人工复核通过插入既有任务时产生与自动派单一致的节点顺序。
- 容量不足、任务状态变化和车辆不一致仍按现有规则拒绝。

### 任务执行测试

- 对相邻同站点上车节点执行一次到站，两者同时进入 `ARRIVED`。
- 两个节点共享同一位置事件和实际到站时间，并分别产生到站审计。
- 两次上车操作分别把两个节点改为 `BOARDED`，分别产生乘客上车审计。
- 不同站点、非相邻节点和下车节点不被到站联动。
- 重复到站请求不重复生成事件或审计。

### 回归测试

- 单订单“发车 → 到站 → 上车 → 到站 → 下车 → 完成”流程保持通过。
- 乘客未出现 5 分钟门禁、二次确认和任务联动保持通过。
- 订单取消、任务资源释放和车辆位置快照保持通过。

## 当前任务安全纠正

代码测试通过并部署到本地试点环境后，再纠正任务 `1626d98d`。纠正过程不通过长期业务接口执行，而使用一次性、可审计的受控数据库事务。

### 纠正前备份

备份以下记录并保存到试运行证据目录：

- 两笔订单；
- 车辆任务；
- 四个任务节点；
- 关联调度决策；
- 关联位置事件；
- 订单和任务审计记录。

备份文件不得包含数据库密码或无关乘客数据。

### 事务前置条件

事务必须逐项断言：

- 任务 ID 为 `1626d98d-d792-4a7d-91eb-40f6ccbba5be`；
- 任务车辆为甘J00856D，任务状态为 `IN_PROGRESS`；
- 两笔订单均属于该任务且状态为 `IN_PROGRESS`；
- 两个上车节点的 `virtualStopId` 完全相同，均为高铁站；
- 第一笔上车节点为 `BOARDED`；
- 第二笔上车节点仍为 `PLANNED`；
- 两个下车节点仍为 `PLANNED`；
- 现有节点顺序仍是 1、2、3、4，且没有新增节点或其他并发操作。

任一条件不满足时，事务立即回滚并停止纠正。

### 纠正内容

- 将第二笔高铁站上车节点调整到第一笔上车节点之后；
- 将第一笔安川下车节点顺延，其余节点保持相对顺序；
- 使用已存在的高铁站到站位置事件和实际到站时间作为第二笔共享到站依据；
- 根据现场确认，把第二笔上车节点补记为 `BOARDED`；
- 为第二笔追加一条纠正型 `PASSENGER_BOARDED` 位置事件：任务节点指向第二笔高铁站上车节点，位置沿用已确认的高铁站位置，`driverReportedAt` 使用现场同时上车的实际时间，`recordedAt` 保留纠正执行时间；
- 追加人工纠正审计，不修改或删除既有审计。

人工纠正审计至少包含：

- 动作 `TASK_COLOCATED_BOARDING_CORRECTED`；
- 原节点顺序和新节点顺序；
- 两笔订单 ID、两个上车节点 ID、共享到站位置事件 ID和纠正型上车位置事件 ID；
- 原因 `COLOCATED_BOARDING_INSERTION_ORDER_CORRECTION`；
- 操作者、执行时间和纠正依据“现场确认两名乘客在高铁站同时上车”。

### 纠正后复核

- 任务时间线显示两个高铁站上车节点均为 `BOARDED`，随后依次为安川和陇阳镇下车节点；
- 两笔订单保持 `IN_PROGRESS`；
- 甘J00856D 保持执行中，不释放车辆或驾驶员；
- 审计中同时保留原始到站、第一笔上车和新增人工纠正记录；
- 第二笔订单存在独立的纠正型 `PASSENGER_BOARDED` 位置事件，可被指标和位置历史追踪；
- 页面下一可执行动作是第一笔安川下车站的“到站”。

## 验收标准

- 同站点插单不再形成“先下车、再返回原站上车”的序列。
- 自动派单和人工复核产生相同的节点插入结果。
- 一次到站可联动相邻同站点上车节点，但每位乘客必须单独确认上车。
- 不同站点和非相邻节点不能被错误联动。
- 当前任务纠正有纠正前备份、严格事务前置条件、原子写入和追加式人工审计。
- API 专项测试、相关回归测试和浏览器验收全部通过后，方可恢复后续真实任务操作。
