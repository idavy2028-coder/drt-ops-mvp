# C1 视频声明链路最小设计（待审阅，2026-09-11）

## 决策与范围

用户已确认首期必须视频监控或视频取证。声明采集是设备能力证据的一层，不能替代收到可播放媒体的验收。建议先批准本设计，再确定首期媒体主路径为实时监控、报警录像取证或两者；本次没有实现视频功能。

最小声明范围：0x9003查询/0x1003声明 → 严格解析 → 当前鉴权设备归属 → 本地可靠队列 → internal API事务 → 能力DECLARED及证据/审计 → 与已配置能力对比 → 独立实测后人工核验VERIFIED。媒体传输、播放器、录像存储、自动赋予角色和配置apply不属于声明功能。

## 消息和安全边界

- jt-protocol中独立codec解析标准音视频属性；ProtocolModuleRegistry仅注册分发。固定标准版本、字段长度、音视频编码枚举、声道/采样参数及通道数边界，拒绝截断、溢出与不支持的扩展。正式标准和厂商差异需在实施前核对，不凭示例反推字段。
- 平台查询生成有界请求记录：设备、当前连接/leaseGeneration、查询时间及超时；回复只在同设备当前鉴权会话内接收。协议没有提供的关联字段不自行假设存在，同连接一次只允许一个未完成属性查询。
- terminalId、系统归属取服务端会话/当前成员，不信任载荷自报ID。声明入口不要求已赋VIDEO角色，以免首次声明形成前置条件循环；但必须校验设备有效、身份、租约/连接代次和限流。
- 成功应答至少要求gateway声明已可靠落盘；不把应答解释为API已写入或能力已核验。API失败时本地重试，明确展示待同步/失败状态。

## 可靠入库与幂等

- 使用独立CAPABILITY_DECLARATION事件，不把声明伪装成SESSION_AUDIT/PROTOCOL_AUDIT。持久化规范化属性、设备ID、消息流水、连接代次、接收时间、载荷摘要及schemaVersion；不保存令牌或原始身份报文。
- 同帧重传幂等键包含设备、连接代次、消息ID、流水及载荷摘要；重复投递使用同一key。重连的新观测可以新增证据，但不重复创建能力事实。
- API在单一事务内取得幂等收据、锁定设备/现有能力、写证据与DECLARED事实、写独立审计、完成收据。失败全回滚；不留“事实已写但审计缺失”的状态。并发同设备能力只产生一条有效事实。
- 重试采用有界退避；临时错误重试，格式错误/过期会话/冲突明确拒绝或进入人工处置，不无限重放。配置发生改变时重新校验，不沿用旧会话映射。

## 状态和配置冲突

| 当前事实 | 新声明处理 |
| --- | --- |
| 无事实 | 有视频通道的声明可建立VIDEO=DECLARED；JT1078媒体属性证据与VIDEO分别记录，不自动推定实测通过 |
| DECLARED | 相同声明幂等；新属性保存观测及变化审计，不重复建事实 |
| VERIFIED | 保留原核验人/时间/证据。新声明与核验事实冲突时记录差异并阻断新的准入决策，不静默覆盖或降级 |
| DISABLED | 不自动复活，记录被阻断的声明，人工处理 |

角色、mediaProfile、通道或编解码与声明不一致时，输出设备级差异及reasonCode；不改manifest，不自动apply配置。实测通过后才调用现有能力核验接口，保留expectedVersion、人员、证据引用和原因；VIDEO不等同于JT1078_MEDIA。没有视频通道不能仅因收到0x1003就声明VIDEO支持。

审计至少区分DECLARATION_RECORDED、DECLARATION_CONFLICT及验证/拒绝原因。记录设备/事实ID、证据摘要、前后状态、关联请求和时间；重复投递不重复写成功审计。

## 存储约束：本轮禁止迁移的影响

代码核对发现gateway_outbox.kind有数据库CHECK白名单，当前没有CAPABILITY_DECLARATION。现有能力表只含枚举、状态及核验证据，不含完整音视频属性；当前能力接口为核验接口，不是设备声明入口。

因此正常扩展可靠outbox链路至少需要另行设计并批准gateway本地队列约束的新增迁移；不能只改Java枚举，更不能修改旧迁移。结构化属性/声明观测可考虑受控证据存储配合现有能力事实，也可另提API声明观测表，取舍取决于查询和保留要求。本轮不新增/修改/执行迁移。若后续仍绝对禁止任何迁移，这条设计只能保持待实施，不能宣称能够在原约束下直接交付。

## 测试与验收

1. codec单元：正常、零视频通道、最大边界、截断/超长、非法编码、未知扩展；独立预期字节样本。
2. gateway集成：未鉴权拒绝、当前租约归属、重连/旧连接拒绝、重传幂等、队列满/不可写不成功应答、重启后重放。
3. API事务：多次投递、并发首次声明、失败回滚、声明与VERIFIED/DISABLED冲突、审计/幂等收据及设备关联。
4. 完整合成TCP→HTTP→隔离数据库→read-back，与现有合成配置对比；人工核验之前保持DECLARED。测试不得把合成结果登记为真实设备实测证据。
5. 经独立授权后，真实设备资料/固件/通道核验及实际媒体验收；本次禁止真实接入。

## 媒体链路是否需要新建

当前仓库实现了部分附件控制/元数据，没有找到完整0x9101实时请求、录像查询/回放控制及媒体接收播放闭环；已有JT1078控制模块明确不在808链接接收原始视频流。没有证据表明现有独立媒体平台可直接复用。

按当前可见资产，需新建或集成：独立媒体接收服务、编解码/播放器或录像下载校验、设备/通道/时间关联、权限与访问审计。若做取证还需对象存储、哈希/不可变证据索引、检索下载和保留策略。可以复用成熟媒体服务，但必须单独验证兼容性及许可证，不能将改ProtocolModuleRegistry视为媒体建设完成。

信令替代方式只是在有实际媒体接收能力时，通过请求→应答→真实流/文件→解码/哈希核验形成证据，再走人工核验。0x9003→0x1003仍是声明路径；通用应答或附件元数据不是视频可用证据。

### 推荐的最小结构变更提案

以下为审阅方案，不是迁移授权；本轮不编写SQL迁移或修改队列白名单。

1. gateway：新增后续本地迁移，扩展gateway_outbox.kind允许CAPABILITY_DECLARATION，保留现有所有kind；旧迁移不变。同步新增独立投递合同，先持久化再应答。上线顺序需兼容旧消费者，未支持的新事件不得作为未知事件成功丢弃。
2. API：推荐新增声明观测表，避免把结构化证据塞入500字符evidenceRef或让外部文件与数据库产生双写。建议字段：id、terminalId、连接代次、消息流水、payloadDigest、规范化attributes JSON、schemaVersion、receivedAt、幂等key、处理结果及冲突reasonCodes；幂等key唯一，按terminalId/receivedAt索引。设备外键和具体DDL待独立评审；不提前指定迁移编号。
3. 接口事务：校验受信gateway和设备/会话关联；唯一收据/观测认领与能力事实、冲突结果、审计在一个事务中提交。相同key相同内容返回原结果；key相同内容不同拒绝。设备行锁串行化首次事实创建，配合现有事实唯一约束核对，不能依赖“查无再插”。
4. 离线重放：明确当前会话校验和可靠队列的冲突。旧代次已落盘观测可保留为历史证据，但不得更新当前能力或用于准入；无法证明会话归属的内容拒绝。不能把所有断线后的待投递数据直接视为当前事实，也不能无条件丢弃已可靠接收的证据。
5. 配置冲突：原VERIFIED事实不被设备声明覆盖；新增未解决冲突必须由preview和apply共同检查，并在apply事务中重新验证，避免preview之后出现冲突仍应用。read-back返回冲突和证据引用。冲突解除要求人工理由和独立审计；此门禁代码属于声明实施范围。
6. 幂等生命周期：流水会回绕；应将服务端查询/观测标识纳入规范化幂等合同，限定重传窗口，避免同连接长期运行后相同流水/内容吞掉新观测。具体0x1003关联能力以正式协议为准，不向协议虚构字段。
7. 拒绝审计与事务失败审计区分：成功事实和成功审计原子提交；无效请求记录受限、安全的拒绝审计，不为匿名垃圾请求无限增长；数据库不可用时不得声称已写审计。
