# 管理端登录故障排查手册

适用范围：本地管理端通过浏览器访问真实 API 时，页面提示登录失败、来源不允许、网络不可用，或认证成功后未进入目标页面。

本手册的目标是先区分故障类型，再执行最小修复。排查过程中不得记录、复制或输出真实密码、访问令牌、刷新令牌、Cookie 或完整认证响应。

## 一、先记录稳定错误代码

登录页会把失败原因分类为稳定错误代码。现场记录错误代码、浏览器地址栏中的协议/主机/端口、发生时间即可，不要截图密码框内容，也不要复制浏览器存储或请求头中的认证数据。

| 错误代码 | 含义 | 首要检查 |
| --- | --- | --- |
| `LOGIN-401` | API 已收到请求，但用户名或密码未通过认证 | 浏览器密码管理器是否提交了旧密码 |
| `LOGIN-ORIGIN-403` | 浏览器来源未被 API 的 CORS 白名单允许 | 地址栏 Origin 是否与白名单逐字匹配 |
| `LOGIN-NETWORK` | 请求未到达可用 API，或前端代理连接失败 | 前端服务、代理目标和 API 健康状态 |
| `LOGIN-NAVIGATION` | 认证已经成功，但前端未能进入目标路由 | 路由配置、用户角色和目标页面权限 |
| `LOGIN-UNKNOWN` | 未归入上述类别的异常 | 浏览器控制台时间点及服务日志中的对应异常类型 |

## 二、按错误代码排查

### `LOGIN-401`：先排除浏览器保存的旧密码

1. 确认用户名无多余空格。
2. 清空密码框后手工逐字输入当前密码，不要依赖自动填充。
3. 如果手工输入可以登录，更新或删除 Chrome 为该站点保存的旧凭据。
4. 只有在确认当前密码确实无效后，才进入正式的密码重置流程。

登录页在收到 401 后会清空密码并把焦点移回密码框，避免旧密码被连续重复提交。

### `LOGIN-ORIGIN-403`：核对精确 Origin

Origin 由“协议 + 主机 + 端口”组成。以下地址彼此不同，必须分别列入允许来源：

- `http://localhost:5174`
- `http://127.0.0.1:5174`
- `http://localhost:5176`
- `http://127.0.0.1:5176`

API 使用 `DRT_WEB_ALLOWED_ORIGINS` 配置允许来源。应把浏览器地址栏的 Origin 与配置项逐字比较，不使用通配符，也不要因为命令行请求成功就判定浏览器来源一定被允许。修改配置后需要按部署方式重新加载 API 服务才能生效。

查看运行容器配置时，只筛选允许来源变量，不要输出整个环境变量集合：

```powershell
docker inspect --format "{{range .Config.Env}}{{println .}}{{end}}" <api-container> | Select-String '^DRT_WEB_ALLOWED_ORIGINS='
```

### `LOGIN-NETWORK`：检查服务链路

按以下顺序检查：

1. 浏览器访问的前端端口是否正在监听。
2. 前端开发代理的 API 目标是否指向当前真实 API。
3. API 健康检查是否成功。
4. 容器端口映射与本机防火墙是否允许该连接。

健康检查示例：

```powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:18081/actuator/health' -TimeoutSec 10
```

健康检查只证明 API 可访问，不证明用户凭据有效，也不证明浏览器 Origin 已获允许。

### `LOGIN-NAVIGATION`：不要误重置密码

该错误表示认证阶段已经成功。先刷新页面，再检查：

1. 是否要求首次修改密码；若是，应进入修改密码页。
2. 登录用户角色是否有目标页面权限。
3. 重定向参数对应的路由是否存在。
4. 前端路由守卫是否出现异常。

不要因为导航失败再次重置密码。若页面仍保持已认证状态，应优先修复路由或权限问题。

### `LOGIN-UNKNOWN`：保留最小诊断信息

记录错误代码、时间、页面地址和复现步骤，在同一时间范围内查找前端控制台与 API 日志。不要把完整认证请求、认证响应或浏览器存储导出到工单或项目文档。

## 三、浏览器失败而命令行成功

出现这一现象时，优先检查两类浏览器特有差异：

1. 浏览器会携带 Origin，命令行工具默认可能不携带，因此命令行成功不能排除 CORS 配置错误。
2. 浏览器密码管理器可能覆盖人工输入或自动提交已保存的旧密码，命令行使用的则是当前输入。

只有在这两项排除后，再检查代理、Cookie 策略、路由守卫和角色权限。

## 四、安全边界

- 禁止直接修改数据库中的密码哈希字段来绕过正常重置流程。
- 禁止伪造访问令牌、刷新令牌或登录态。
- 禁止在源码、提交记录、截图、日志摘录或排障文档中保存真实凭据。
- 禁止为验证错误提示而连续尝试正式账号密码，避免触发锁定或产生不必要的审计记录。
- 需要端到端成功登录时，应使用经批准的受控测试账号；不得读取或代填用户的正式密码。

## 五、修复后的回归检查

完成配置或代码修复后，至少验证：

1. 401 被标记为 `LOGIN-401`，密码框被清空并重新聚焦。
2. 不允许的来源被标记为 `LOGIN-ORIGIN-403`，页面不误报密码错误。
3. 网络故障被标记为 `LOGIN-NETWORK`。
4. 首次改密用户直接进入修改密码页。
5. 认证后导航失败被标记为 `LOGIN-NAVIGATION`，不清除已建立的认证状态。
6. 允许来源只包含明确的本地地址，不包含通配符。
